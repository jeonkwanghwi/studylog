### 1.1 결제 모델 전환 — 선 결제, 후 페이백

**바뀐 것.** 유저는 챌린지에 **참가비를 먼저 낸다.** 목표를 달성한 날마다 하루치가
크레딧으로 돌아오고, 실패한 날의 몫은 서비스에 귀속된다.

**왜.** 기존 모델은 유저가 실패한 뒤에 지갑을 열어야만 매출이 생겼다. 실패 직후는
지불의사가 높지만 동시에 이탈 의사도 높은 순간이고, 무엇보다 **성실한 유저에게서는
한 푼도 나오지 않으면서 AI 원가는 그대로 발생**했다. 선결제는 현금이 먼저 들어오고,
이미 낸 돈이 사라지는 걸 매일 보는 손실회피가 매일 오는 방어보다 강하다.

**왜 현금이 아니라 크레딧인가.** 1부 결정 2가 보증금 환급 모델을 버린 이유가 그대로
살아있다 — 돈이 유저에게 되돌아가면 선불전자지급수단 발행으로 **전자금융업 등록
대상**이 될 수 있고, 앱스토어 심사에서 도박성 판정 위험도 커진다. 페이백을 인앱
크레딧으로 하면 **돈은 서비스에 귀속된 채로 남고** IAP 밖으로 나가지 않는다.
현금 환급은 PG 별도 계약 + 전자금융업 등록 + 애플 심사 리스크를 한꺼번에 지는 일이라
동기부여 이득에 비해 값이 너무 비싸다.

**절대 넘지 않는 선 (규제 전제).** 아래 넷은 기능 결정이 아니라 *등록·신고 의무를
발생시키지 않기 위한 전제*다. 하나라도 깨면 전자금융업 등록이나 PG 계약이 따라온다.

1. **모든 결제는 앱스토어/구글 IAP로만 받는다.** 애플·구글이 판매자(Merchant of
   Record)이므로 우리가 PG 계약을 맺거나 결제대행 신고를 할 일이 없다. 자체 결제창,
   계좌이체, 외부 결제 링크는 만들지 않는다.
2. **크레딧은 현금으로 환급되지 않는다.** 인출·송금·상품권 교환 모두 없다.
3. **크레딧은 스터디로그 안에서만 쓰인다.** 제휴처·외부 가맹점에서 쓸 수 없다.
   전자금융거래법의 선불전자지급수단은 "발행자 외의 제3자에게서 재화·용역을 살 수
   있거나 현금으로 환급되는 것"이 대상인데, 2와 3이 그 정의를 벗어나게 한다.
4. **유저 간 금전 이동이 없다.** 누구의 참가비도 다른 유저에게 가지 않는다.
   실패분은 전액 서비스에 귀속된다. 이것이 벌금 풀 분배 모델과의 결정적 차이다.

크레딧 현금 인출, 유저 간 선물하기, 외부 제휴 사용처는 전부 **v1 이후로도 금지**다.
넣으려면 그때 법률 검토를 먼저 받아야 한다.

**패스권은 사라진다.** 재화를 크레딧 하나로 통합한다. 선결제 모델에서는 "실패한 날을
미리 방어한다"는 개념 자체가 필요 없다 — 이미 돈을 냈고, 실패하면 그 몫이 안 돌아오는
것이 곧 벌칙이다.

`02-open-questions.md`에서 방향을 뒤집은 것은 §8에 따로 정리했다.

## 4. 핵심 흐름

### 4.1 세션

```
POST /sessions/start   (multipart: image)
  → 리사이즈 → S3 업로드 → photos 행 생성(received_at = 요청 도착 시각)
  → AI 판정 (동기)
      pass → study_sessions 생성 (status=open, started_at=received_at)
      fail → 세션 생성 안 함. 재촬영 요구 + 이의제기 가능

POST /sessions/{id}/end   (multipart: image)
  → 동일 → AI 판정
      pass → status=closed, counted_minutes = min(ended_at - started_at, 240)
      fail → 세션은 open 유지. 재촬영 요구 + 이의제기 가능
```

하루 여러 세션 허용, 정산 시 합산 (결정 6).

**미종료 세션** — 시작 +4시간에 `abandoned`, `counted_minutes = 0`.
+3시간 30분에 경고 푸시를 보낸다(§5). 경고 없이 3시간 공부가 증발하면 이탈 사고가 된다.

### 4.2 이의제기

```
POST /photos/{id}/appeal   (body: text)
  → 해당 사진의 attempt=2 판정 실행. 프롬프트에 유저 설명을 첨부
  → pass면 원래 샷의 역할대로 처리된다 (시작 샷이면 세션 생성, 종료 샷이면 close)
  → 결과가 최종. 재이의 없음
```

**이의제기가 만들어내는 시각은 항상 유저에게 불리한 쪽으로 잡는다.**

| 재판정 대상 | 채택 시각 |
|---|---|
| 시작 샷 | `started_at` = **재판정 시각** (늦은 쪽) |
| 종료 샷 | `ended_at` = **최초 수신 시각** (이른 쪽) |

시작 샷에 최초 수신 시각을 쓰면 "시작 샷 찍고 3시간 놀다가 이의제기로 통과 → 3시간 적립"이
성립한다. 종료 샷에 재판정 시각을 쓰면 이의제기를 오래 끌수록 시간이 늘어난다.
양쪽 다 불리한 시각을 택하면 이의제기로는 1분도 벌 수 없고, 정상 유저는 손해가 없다.

이의제기 가능 시한은 **해당 하루의 04:00 정산 전까지**다. 정산된 날은 닫힌다.

### 4.3 정산 (매일 04:00 KST, 서버 cron)

전날 04:00 ~ 오늘 04:00 사이에 `closed`된 세션의 `counted_minutes` 합계로 유저당 1행을 만든다.

```
total >= goal   → success, streak += 1
                  활성 챌린지가 있으면 daily_payback 만큼 크레딧 적립
total <  goal   → failed,  streak = 0,  피드에 "✗ 미인증" 박제
                  적립 없음 — 그 몫은 서비스에 귀속된다
```

**`passed`는 정산에서 더 이상 나오지 않는다.** 사전 방어(패스권 자동 차감)가 사라졌기
때문이다. `passed`는 이제 사후 복구(§4.4)로만 만들어진다.

챌린지가 `ends_on`에 도달하면 그날 정산에서 `completed`로 닫는다. 전일 `success`였고
`paid_with == "iap"`이면 `completion_bonus`를 추가 적립한다.

모든 경우에 정산 후 `streak_count`를 `streak_snapshot`에 기록하고,
`pending_goal_minutes`가 있으면 `daily_goal_minutes`로 승격시킨다(§4.7).
크레딧 증감은 전부 `credit_ledger`에 기록한다.

### 4.4 streak 복구 (결정 14 — 핵심 매출 지점)

`failed` 레코드에 대해 **정산 후 24시간 내**, `credit_balance >= 2000`이면:

```
credit_balance -= 2000        # credit_ledger에 reason="restore"로 기록
result = passed
streak_count = (전날 daily_record.streak_snapshot) + 1     # 전날 레코드가 없으면 1
```

**복구해도 그날의 페이백은 돌아오지 않는다.** `payback_amount`는 0으로 남는다 —
되사는 것은 연속 기록이지 그날의 성과가 아니다.

복구 비용 ₩2,000이 하루 페이백 ₩1,000보다 비싼 것은 의도된 것이다. 산술적으로는
손해이고, 그럼에도 지불한다면 그건 streak 자체에 값을 매긴 것이다.

### 4.5 결제

상품은 **기간 × 하루 배팅액**의 2차원이다. 기간만 있으면 "얼마나 오래"만 고를 수
있지만, 배팅액이 붙으면 "얼마나 진심인지"를 고르게 된다 — 동기부여 강도를 유저가
직접 정한다.

| SKU | 기간 | 하루 배팅 | 참가비 | 완주 보너스 |
|---|---|---|---|---|
| `challenge_7d_1k` | 7일 | ₩1,000 | ₩7,000 | — |
| `challenge_7d_2k` | 7일 | ₩2,000 | ₩14,000 | — |
| `challenge_7d_3k` | 7일 | ₩3,000 | ₩21,000 | — |
| `challenge_14d_1k` | 14일 | ₩1,000 | ₩14,000 | ₩700 |
| `challenge_14d_2k` | 14일 | ₩2,000 | ₩28,000 | ₩1,400 |
| `challenge_14d_3k` | 14일 | ₩3,000 | ₩42,000 | ₩2,100 |
| `challenge_30d_1k` | 30일 | ₩1,000 | ₩30,000 | ₩3,000 |
| `challenge_30d_2k` | 30일 | ₩2,000 | ₩60,000 | ₩6,000 |
| `challenge_30d_3k` | 30일 | ₩3,000 | ₩90,000 | ₩9,000 |

**완주 보너스는 기간에 비례한 비율이다 — 7일 0% / 14일 5% / 30일 10%.** 배팅액이
변수가 된 이상 정액 보너스는 성립하지 않는다. 7일은 완주가 쉬워 보너스 없이도 팔리고,
30일은 보너스가 있어야 도전할 이유가 생긴다.

> **스토어 가격과 1원까지 일치해야 한다.** `CHALLENGE_PRODUCTS`의 `price`는 애플·구글에
> 실제 등록된 가격과 같아야 하며, 다르면 `entry_amount`가 거짓을 기록하고 페이백 총액이
> 실제 결제액과 어긋난다. 등록 불가능한 티어가 있으면 **가격을 맞추는 게 아니라 하루
> 배팅액을 조정**해서(예: ₩2,900) 참가비가 티어에 떨어지게 한다.

**크레딧으로 참가한 챌린지에는 완주 보너스를 주지 않는다.** 안 그러면 완주자가
크레딧을 무한 증식시켜서 영구히 이득만 보는 경로가 열린다. `paid_with`가 이걸 가른다.

**크레딧은 현금화되지 않고 유효기간이 6개월이다.** 다음 챌린지 참가비로만 쓰이거나
streak 복구에 쓰인다. 이 두 가지가 규제 노출을 막는 핵심 설계다.

검증은 **RevenueCat**에 맡긴다. 웹훅 수신 → `revenuecat_event_id` 중복 확인 →
`challenges` 행 생성(`status=active`, `paid_with=iap`) + `purchases` 행 생성.
클라이언트가 "샀다"고 말하는 것은 신뢰하지 않는다.

**환불되면 챌린지를 무효화한다.** `status=refunded`로 닫고, 그 챌린지가 적립한 크레딧을
`credit_ledger`에 `reason="refund"`인 음수로 회수한다. 잔액이 음수가 되면 0으로 막고
계정에 플래그를 남긴다. 선결제 모델에서는 환불이 곧 참가 취소이므로, 기존의
"회수하지 않는다"는 규칙은 여기서 성립하지 않는다.

**심사 대응 문구** — "챌린지 참가비는 유저 간 금전 이동이 없는 인앱 소모성 아이템이며,
페이백은 현금이 아니라 현금화 불가능한 인앱 크레딧이다. 결과는 전적으로 본인의
행동으로 결정되며 우연 요소가 없다." 세 문장이 각각 자금이체·환금성·사행성을 막는다.

### 4.6 피드

그룹별. 항목 하나 = 한 유저의 하루 = 사진들 + 누적 시간 + 결과 + streak 배지.
**사진은 그룹원에게 전부 공개된다.** pHash·EXIF 자동 차단을 v1에서 빼기로 했으므로
(§8) 부정행위를 실제로 억제하는 것은 상호 감시다.

세션이 `closed`되면 즉시 피드에 뜨고, `✗ 미인증` 박제는 04:00 정산 후에 붙는다.

**순위표는 만들지 않는다.** 목표가 개인별이라 절대 시간으로 줄 세우면 직장인이 영원히
꼴찌고(결정 9의 취지가 사라진다), 달성률·streak 기준은 목표를 낮게 잡을수록 유리해서
어뷰징된다. 경쟁은 피드의 streak 숫자 비교로 자연 발생시킨다.

### 4.7 목표 시간 변경

유저가 목표를 바꾸면 `pending_goal_minutes`에만 쓰고, **04:00 정산 배치가 그날 정산을
끝낸 뒤** `daily_goal_minutes`로 승격시킨다. 즉 **변경은 항상 다음 날부터 적용**된다.

즉시 반영하면 밤 10시에 목표를 10분으로 낮춰 무조건 `success`를 만들 수 있다.
개인별 목표(결정 9)를 도입한 이상 이 구멍은 반드시 막아야 한다. 컬럼 하나로 끝난다.

## 5. 알림

| 시점 | 대상 | 내용 |
|---|---|---|
| 세션 시작 +3h30m | 해당 유저 | "30분 뒤 자동 폐기됩니다" |
| 22:00 | 오늘 목표 미달자만 | 마감 리마인드 |
| 판정 fail 즉시 | 해당 유저 | 앱을 닫은 뒤 fail이 나면 세션이 통째로 날아간다 |
| 08:00 | 어제 `failed`인 유저만 | streak 끊김 + 놓친 페이백 + 복구 유도. **매출 직결** |
| 챌린지 종료일 08:00 | 챌린지를 끝낸 유저 | 총 페이백 결과 + 재참가 유도. **매출 직결** |

정산 자체(04:00)는 알리지 않는다. 달성한 날에도 알리지 않는다.

08:00 알림 문구에는 **놓친 금액을 명시**한다 — "어제 ₩1,000을 놓쳤어요"가
"연속 기록이 끊겼어요"보다 구체적이고, 선결제 모델에서는 실제로 일어난 일이다.

**친구 인증 알림은 넣지 않는다.** 그룹 5명 × 하루 2세션이면 하루 16통이고,
다중 그룹이면 그 배수가 된다. 알림 피로가 즉시 온다. 앱을 열면 피드에 다 보인다.

## 6. AI 판정

### 6.1 어댑터

```
JudgeProvider.judge(image_bytes, context) -> Verdict
    ├ providers/claude.py      ← v1 기본값
    ├ providers/openai.py
    └ providers/gemini.py
```

`JUDGE_PROVIDER` / `JUDGE_MODEL` env로 교체. 프롬프트 텍스트는 프로바이더가 공유한다(공정 비교 전제).

**v1 기본값: `claude-haiku-4-5`.**

### 6.2 이미지 전처리

업로드 즉시 서버가 **긴 변 1280px, JPEG q80**으로 리사이즈한다. 원본은 남기지 않는다.

장당 2MB → 약 200KB. S3 비용이 1년 누적 기준 월 $66에서 월 $7 수준으로 떨어지고,
**vision 입력 토큰이 함께 줄어 AI 원가에도 직결된다.** 판정에 1280px면 차고 넘친다.

### 6.3 판정 정책

**pass 범위는 넓게.** 책상·도서관·카페에서 무언가에 집중하는 장면이면 통과시킨다.
종이책, 노트북 코딩, 태블릿 필기, 인강 모두 포함한다. 게임 화면·예능·SNS·음식·
사람 얼굴만 확실한 fail이다. 좁게 잡으면 직장인과 개발자를 통째로 잃는다.

**모니터에 띄운 사진이나 인쇄물을 재촬영한 것은 fail이다.** pHash·EXIF 차단을
v1에서 빼기로 했으므로, 재촬영 감지는 프롬프트가 담당하는 유일한 방어선이다.

### 6.4 출력 스키마

structured output으로 고정한다.

```json
{
  "decision": "pass" | "fail",
  "confidence": 0.0 ~ 1.0,
  "reason": "한국어 한 문장"
}
```

응답 전문은 `verdicts.raw_json`에 저장한다.

### 6.5 임계값 — 관대하게

```
decision == "fail" AND confidence >= 0.7   → fail
그 외 전부                                  → pass
```

즉 **확신하는 fail만 거른다.** 애매하면 전부 통과시킨다. 어뷰징 일부를 감수하는
대신 정상 유저 오차단을 막는다. 초기에 가장 큰 이탈 원인은 어뷰저가 아니라
"제대로 공부했는데 fail 났다"이다.

`0.7`은 초기값이며 env로 조정한다. `verdicts`가 쌓이고 이의제기가 정답 라벨을
만들어주면 데이터로 다시 정한다.

### 6.6 타임아웃

10초. 초과하면 **pass 처리**하고 로그를 남긴다. 관대 원칙의 연장이며,
AI 장애로 유저의 공부 시간이 날아가는 상황을 막는다.

## 7. 단위경제학 — 모델 선택의 근거

AI 판정은 매출과 무관하게 **유저 수에 정비례하는 순수 원가**다. 챌린지에 참가하지 않는
무료 유저도 매일 비용을 발생시킨다.

1,000명 기준 월 원가 (하루 4장 가정, 리사이즈 전):

| 모델 | 월 원가 | 손익분기에 필요한 유료 매출 (전환율 10% 가정) |
|---|---|---|
| `claude-opus-5` | 약 200만원 | 인당 월 2만원 — 불가능 |
| `claude-sonnet-5` | 약 80만원 | 인당 월 8,000원 — 빠듯 |
| `claude-haiku-4-5` | 약 40만원 | 인당 월 4,000원 — 가능 |

**선결제 전환이 이 그림을 바꿨다.** 이제 매출은 실패한 유저가 지갑을 여느냐가 아니라
**참가비가 먼저 들어오고 그중 얼마가 안 돌아가느냐**로 결정된다.

30일 챌린지 100명, 일일 달성률 70%를 가정하면:

| | |
|---|---|
| 선입금 | ₩3,000,000 |
| 페이백 (성공 2,100일 × ₩1,000) | ₩2,100,000 (크레딧, 현금 유출 아님) |
| **서비스 귀속** | **₩900,000** |
| AI 원가 (haiku, 100명 월) | ₩40,000 |

기존 모델은 성실한 유저에게서 매출이 0이면서 AI 원가는 그대로 나갔다. 선결제는
**참가한 순간 전원이 매출**이고, 페이백은 크레딧이라 현금이 나가지 않는다.

그래도 두 가지는 그대로다.

1. **모델은 haiku급이어야 한다.** AI 원가는 여전히 유저 수에 정비례하고, 챌린지에
   참가하지 않는 무료 유저도 매일 판정 비용을 발생시킨다.
2. **일일 페이백은 참가비를 일수로 나눈 값을 넘지 않는다.** 넘으면 완주자가 낸 돈보다
   많이 받아가고, 크레딧 재참가와 결합되면 무한 증식이 된다. 완주 보너스를
   현금 참가에만 주는 규칙이 이 구멍을 막는 장치다.

§6.2의 리사이즈가 AI 원가를 추가로 낮춘다.
