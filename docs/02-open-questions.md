# 미결 안건 — 브레인스토밍 2부

1부에서 제품의 뼈대(인증 단위 · 판정 권한 · 실패 대가 · 아키텍처)는 확정됐다.
2부는 그 뼈대에 붙는 나머지를 정한다. 아래 순서대로 진행할 예정.

---

## A. 부정행위 방지

AI 모델 등급으로는 해결되지 않는 영역. 1부에서 방향만 잡고 미확정으로 남겼다.

- 카메라 직접 촬영만 허용하고 갤러리 선택을 차단할 것인가 (RN ImagePicker 제약)
- pHash 중복 검사 범위 — 본인 과거 사진만? 그룹 내 타인 사진까지?
- EXIF 촬영시각과 서버 수신시각의 허용 오차 (초과 시 reject)
- 모니터에 띄운 사진·인쇄물 재촬영 감지를 판정 프롬프트에 포함할 것인가

## B. 결제 상세

- 패스권 SKU 구성과 원화 가격 (3개/10개 묶음)
- streak 복구권을 별도 SKU로 팔 것인가, 일반 패스권과 같은 재화로 쓸 것인가
- IAP 영수증 서버 검증 (App Store Server API / Google Play Developer API)
- 환불·결제 취소 시 이미 소비한 패스권 회수 정책
- **앱스토어 심사 리스크 점검** — "친구들끼리 돈 걸고"가 도박성으로 오해받을 여지.
  현 모델은 유저 간 정산이 없어 도박이 아니지만, 심사원 설득용 문구가 필요할 수 있음

## C. 소셜 / 랭킹

- **목표가 개인별인데 랭킹을 뭘로 매기나.** 절대 공부시간으로 매기면 직장인이 영원히
  꼴찌라 개인별 목표를 도입한 의미가 사라진다. streak 기준? 달성률? 주간 총 시간 병기?
- 피드 노출 범위 — 사진을 그룹원에게 다 공개할 것인가, 결과만 보여줄 것인가
- 박제 표현 수위 (수치심이 동력이지만 과하면 이탈)
- 그룹 초대 딥링크 설계 (설치 전 클릭 → 설치 후 초대코드 유지)

## D. 애매 판정 투표 UX

- 정족수와 마감 시간
- 아무도 투표하지 않으면 어떻게 처리하나 (기본 pass? 기본 fail?)
- 투표 요청 알림이 스팸이 되지 않게 하는 법

## E. 알림 설계

- 마감 전 리마인드 타이밍 (하루 경계가 새벽 4시임을 감안)
- 친구 인증 알림으로 경쟁심리를 자극할 것인가 vs 알림 피로도

## F. 판정 프롬프트

- pass 인정 범위 — 종이책 / 노트북 코딩 / 태블릿 필기 / 학원 / 도서관 / 독서실
- confidence 임계값 초기값 (상한·하한)
- 출력 스키마 (structured output으로 고정)

## G. 온보딩 / 인증

- 로그인 방식 (Apple / Google 소셜)
- 최초 흐름 — 그룹 생성인가 초대코드 가입인가, 목표 시간 설정 시점

## H. MVP 범위 확정

무엇을 1차 출시에 넣고 무엇을 뺄지 명시적으로 자를 것.

## I. AWS 구성 상세

- S3 presigned upload (앱 → S3 직접 업로드, 서버는 키만 발급)
- RDS 인스턴스 사양, 백업
- 정산 배치 스케줄러 (cron? EventBridge?)
- 시크릿 관리 (AI API 키, IAP 검증 키)
