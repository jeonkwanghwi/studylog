## 2. 앱스토어 가격 티어 확인 필요

상품표가 이 가격을 전제한다. **스토어에 없는 티어면 가격이 아니라 하루 배팅액을 조정**해야 한다
(참가비 = 일수 × 배팅액이 깨지면 "낸 만큼 돌려받는다"는 약속이 깨진다).

```
7,000  14,000  21,000  28,000  30,000  42,000
```

특히 **21,000 / 42,000** 이 한국 티어에 있는지 확인해달라. 없으면 하루 3,000원을
2,900원 같은 값으로 내려서 맞춘다.

## 2.8 약관·개인정보처리방침 — 화면은 만들었고, 내용은 네가 채워야 한다

앱스토어는 개인정보처리방침을 **필수**로 요구한다. 그리고 로그인 화면이
"계속하면 이용약관과 개인정보처리방침에 동의하는 것으로 봅니다"라고
적어놓고 **정작 그 문서가 없었다.** 없는 문서에 동의를 받고 있었던 셈이다.

이제 `/legal/terms`, `/legal/privacy` 로 실제로 열린다. 로그인 화면과
설정 화면 양쪽에서 닿는다(가입 후에는 로그인 화면을 다시 볼 수 없다).

**수집 항목은 지어내지 않고 코드에서 확인해 적었다** — 카카오에 `openid`
스코프만 요청하고 서버는 id_token 의 sub 하나만 저장한다. 이메일·실명·
프로필을 받지 않는다는 사실을 명시했고, 코드와 어긋나면 허위 고지가
되므로 테스트로 묶어놨다.

→ **네가 채워야 할 것** (`app-client/src/legal/content.ts` 의 `[입력 필요]`).
   사실이어야 하는 값이라 내가 지어낼 수 없다:

   - 상호 / 대표자 / 사업자등록번호 / 주소 / 문의처
   - 개인정보 보호책임자와 연락처
   - 인증 사진·이용 기록의 보관 기간
   - 판정에 쓰는 AI 제공업체 이름 (모델을 정하면 확정된다)
   - 약관 시행일, 변경 공지 유예일수

   화면에서 아직 안 채운 항목은 **붉게 표시**되고 상단에 경고가 뜬다 —
   조용히 넘어가서 그대로 제출되는 것을 막기 위해서다.

   **개인 개발자로 출시하기로 정했다(2026-09-20).** 그래서 상호·사업자등록
   번호는 문서에서 뺐다 — 없는 번호를 적는 것 자체가 허위 표시다. 남은 것은
   개발자명, 문의처(이메일), 시행일, 보관 기간, AI 제공업체 이름뿐이다.

   > 확인이 필요한 것: 인앱결제는 스토어가 결제를 처리하고 대금을 정산하는
   > 구조라 개인 개발자로 출시하는 사례가 일반적이다. 다만 국내에서
   > 통신판매업 신고가 필요한지는 판매 주체를 누구로 보느냐에 달려 있고,
   > 이건 내가 판단할 수 있는 영역이 아니다. 매출이 생기기 전에 한 번
   > 확인해두는 게 좋다.

## 3. 번들 ID — 확정됨

**`com.kwanghwi.studylog`** (iOS·Android 동일).

원래 `com.studylog.app` 으로 잡았는데 **Apple 에 이미 선점돼 있었다.** App ID 는
전 세계에서 유일해야 해서 흔한 이름은 대부분 나가 있다. 도메인을 소유하지
않았으므로 개인 개발자 관례대로 이름 기반으로 정했다.

**이건 사실상 되돌릴 수 없다.** 출시 후 바꾸면 완전히 다른 앱이 되고 기존
설치·리뷰·구매가 전부 끊긴다. 지금이 바꿀 수 있는 마지막 시점이다.

같은 값을 쓰는 곳이 세 군데다 — 하나라도 어긋나면 조용히 깨진다:

| 위치 | 무엇이 깨지나 |
|---|---|
| `app-client/app.json` | 빌드 자체가 안 된다 |
| 서버 `APPLE_BUNDLE_ID` | Apple 로그인 id_token 의 audience 검증 실패 → 로그인 불가 |
| RevenueCat 앱 설정 | 결제는 되는데 웹훅이 안 맞아 챌린지가 안 열린다 |

앱 이름(스터디로그)과 카피는 아직 미정이다. 번들 ID 와 무관하니 나중에
바꿔도 된다.

## 4. AWS 배포 — 같이 하기로 한 것

준비는 다 됐다. `server/deploy/runbook.md` 에 절차가 있고, 필요한 건:
- Lightsail t4g.small + RDS db.t4g.micro + S3 (월 $15~25 예상)
- **배포 전 `alembic check` 필수** — 마이그레이션이 손으로 작성됐고 진짜 Postgres에서
  한 번도 안 돌았다
- **FOR UPDATE 동시성이 실제 Postgres에서 미검증** — SQLite에선 락이 no-op이라
  테스트로 증명이 안 된다. 배포 후 확인해야 할 유일한 항목

## 5. 결정했지만 되돌릴 수 있는 것 (참고)

레저에 근거와 "틀렸을 때 비용"까지 적어뒀다. 특히 이 셋은 제품 방향이라 이견 있으면 말해달라.

- **홈의 가장 큰 숫자를 "돌려받은 돈"이 아니라 "아직 못 받은 돈"으로** — 손실회피 프레임.
  앱을 여는 것 자체가 부담스러워질 위험은 있다
- **되산 날(복구)은 완주로 안 쳐서 완주 보너스를 못 받는다** — 챌린지 막바지 복구 매출이 준다
- **전패해도 첫 챌린지 상한(3만원)이 풀린다** — 상한이 막으려던 건 실력이 아니라 경험 부족이라고 봤다

## 6. 판정 실측 결과 (2026-09-11, gpt-4o-mini)

선언 기반 판정으로 바꾼 뒤 실제 사진 10건을 돌렸다. **호출이 실제로 닿은 9건은 전부 정확**,
응답 1.5~3.5초. 실패한 1건은 판정 오류가 아니라 레이트 리밋이다(아래).

| 사진 | 선언 | 기대 | 결과 |
|---|---|---|---|
| 책상 위 책 | 공부 | 통과 | 통과 0.80 |
| 노트 필기 | 수학 문제집 풀기 | 통과 | 통과 0.70 |
| 노트북 코딩 | 코딩 | 통과 | 통과 0.90 |
| 도서관 | 책읽기 | 통과 | 통과 0.85 |
| 헬스장 | 운동 | 통과 | 통과 0.90 |
| 러닝 | 런닝머신 30분 | 통과 | 통과 0.70 |
| 헬스장 | **공부** | 거절 | 거절 0.90 |
| 책상 위 책 | **운동** | 거절 | 거절 0.90 |
| 음식 | 공부 | 거절 | 거절 0.95 |
| 풍경 | 책읽기 | 거절 | 거절 0.80 |

핵심은 아래 두 줄이다. **같은 사진이 선언에 따라 정반대로 판정된다** — 헬스장 사진은
"운동"이면 통과, "공부"면 거절. 선언 없이는 표현할 수 없던 판정이다.

**남은 위험 — 레이트 리밋이 곧 무조건 통과다.**
10건 중 1건이 429로 떨어졌고, 관대 폴백이 확신 0.00으로 통과시켰다. 설계대로지만
뒤집으면 **판정이 통째로 꺼지는 상황**이다. 유저가 몰리는 저녁 시간대에 이게 나면
그날 인증이 전부 공짜로 통과한다.

지금까지 한 것:
- 429·5xx 는 지수 백오프로 최대 3회 재시도한 뒤에만 폴백한다(10초 예산 안에서)
- SDK 자체 재시도(기본 2회)를 껐다 — 겹치면 한 번 판정에 최대 9번 호출이 나가고
  예산을 다 먹는다

**그래도 남는 것:** 이번 429는 조직 전체 TPM 한도(200k/분)가 이미 꽉 찬 상태라
재시도로 뚫리지 않았다. 테스트용 키를 다른 용도와 공유해서 생긴 일일 수도 있지만,
사진 판정은 이미지 토큰이 커서 실서비스에서도 TPM이 먼저 막힌다.

→ **네가 정해야 할 것:** 판정 모델을 gpt/claude/gemini 중 무엇으로 갈지, 그리고
   그 계정의 TPM 한도를 실제 동시 유저 수 기준으로 확인해야 한다. 저녁 피크에
   판정이 꺼지면 그날 매출이 전부 페이백으로 나간다.
